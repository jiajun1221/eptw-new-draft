1 Executive summary

The current application is a frontend-only functional prototype for an Electronic Permit-to-Work system. It demonstrates permit screens, dynamic templates, role-aware navigation, approval stages, operational states, revisions, checklists, and administration pages. It does not include a server, database, real authentication, durable file storage, notification service, production audit service, or deployment pipeline.

The existing TypeScript domain code should be treated as a draft functional specification. It is useful for identifying expected behaviour and frontend contracts, but it is not a security boundary. The backend must independently validate identity, authorization, object access, transition rules, input data, concurrency, and audit events.

The cleanest integration path is to retain the PermitRepository interface and replace the localStorage implementation with an HTTP-backed repository. This approach limits unnecessary UI changes while moving authority to the server.

Immediate handoff priorities

  • Resolve the untracked duplicate src/App.tsx file that currently breaks TypeScript compilation and the handoff structure check.
  • Fix the remaining UI test failure and rerun the full verification suite.
  • Correct stale role checks that currently hide activity logging and the audit page.
  • Confirm parent and child permit lifecycle rules before they are encoded in a database.
  • Commit and tag a clean, reproducible handoff revision.

5 Functional scope

Implemented prototype behaviour

  • Mock login, Micron registration, contractor registration, and tutorial screens
  • Role-specific navigation and dashboard views
  • Parent and child permit registers
  • Permit creation, editing, duplication, and owner draft deletion
  • Dynamic parent and child permit templates with sections, tabs, custom fields, permissions, and child-template attachment
  • Individual Reviewer, MT Group, and PM approval stages
  • Permit revision history, expiry, activation, suspension, resumption, closure, rejection, and cancellation rules
  • Safety checklist selection and conditional validation
  • Activity logs and locally generated audit events
  • Companies, sites, users, disciplines, and MT Group administration
  • Analytics, LSS/FAS, SIPP, resource library, and browser-print demonstrations

Prototype only or incomplete

  • The SSO screen only checks the email domain and does not contact an identity provider.
  • Contractor registration does not create a durable account or approval request.
  • Uploads are held in browser memory or data URLs rather than transferred to file storage.
  • Notifications are not connected to email, messaging, or an event service.
  • Several destinations display reserved module placeholders.
  • PDF export uses the browser print dialog rather than a controlled document-generation service.
  • Analytics and reporting operate on seeded or browser-local data.

Every server-side transition should verify the persisted status, authenticated actor, role assignments, separation of duties, required comments, date boundaries, and concurrent updates in one transaction. The API must not accept an arbitrary new status from the browser.

Dynamic templates

Templates can be parent or child templates. A template contains sections, optional tabs, field definitions, required flags, option lists, layout information, section edit access, and child-template references. Permit responses to dynamic fields are stored in a customFields map.

The backend should version templates. Each submitted permit revision must retain the exact template version and field definition used at submission time so that later template changes do not alter historical records.

10 Authentication and security

Current state

  • The prototype trusts the browser to select an identity and role.
  • The Micron login demonstration only validates an email suffix.
  • There are no sessions, signed tokens, password controls, MFA, account lockout, or identity-provider calls.
  • Route guards and hidden buttons are not authorization controls.
  • Audit records can be changed or deleted with browser storage tools.

Production requirements

  • Integrate the approved corporate OIDC or SAML identity provider for Micron users.
  • Define the identity, registration approval, password, and recovery process for contractors.
  • Derive roles, site access, company scope, assignments, and MT Group membership on the server.
  • Authorize every endpoint and scope every object query to the authenticated user.
  • Enforce separation of duties and transition rules on the server.
  • Validate every request against a documented schema.
  • Use restrictive CORS, CSRF protection where applicable, rate limits, security headers, and centralized error handling.
  • Scan uploads for malware and enforce content type, extension, and size rules.
  • Keep workflow and security audit events append-only.

11 Recommended backend architecture

A conventional service architecture is sufficient for the first production release. The frontend should call a documented HTTP API. The API should own authentication context, authorization, workflow commands, database transactions, audit generation, attachment metadata, and notification events.

React frontend
  -> HTTP API
      -> Identity and authorization
      -> Permit workflow service
      -> Template and directory services
      -> Relational database
      -> Object storage for files
      -> Notification outbox and workers
      -> Central logging and monitoring

Frontend integration seam

Preserve the PermitRepository method surface where practical and implement an HTTP repository behind it. React components should request operations through the repository or feature-specific client services rather than reading localStorage directly.

Operational requirements

  • Use database transactions and row locking or optimistic concurrency for permit transitions.
  • Use idempotency keys for commands that may be retried.
  • Generate permit numbers through a database sequence or dedicated numbering service.
  • Store timestamps in UTC and format user-facing values for Asia/Singapore.
  • Use an outbox pattern for notifications after committed workflow changes.
  • Provide structured logs, trace IDs, metrics, alerting, backups, and restore procedures.

12 Recommended database design

A relational database such as PostgreSQL is a strong fit because permits have structured ownership, revision, approval, and parent-child relationships. JSON or JSONB can hold dynamic template definitions and dynamic answers while core workflow data remains relational.

Table or aggregatePurpose
users, roles, user_rolesIdentity profiles and application roles
companies, sites, user_sitesOrganization and access scope
disciplinesControlled permit discipline directory
mt_groups, mt_group_membersReview groups, membership, and closure authority
templates, template_versionsVersioned form definitions and publication state
permitsStable permit identity, number, ownership, and parent relationship
permit_revisionsControlled revision records and dynamic answers
approval_stagesStage assignment, decision, actor, date, and comment
activity_logsDaily operational and safety records
audit_eventsAppend-only lifecycle and security history
attachmentsFile metadata, storage key, hash, scan status, and retention state
notification_outboxReliable post-transaction notification delivery

Important constraints

  • Use UUIDs internally and a separate human-readable permit number.
  • Add foreign keys and unique constraints for permit numbers and revision numbers.
  • Index status, site, company, requestor, reviewer, MT Group, dates, and parent permit.
  • Prevent submitted historical revisions from being silently overwritten.
  • Snapshot template version references on every permit revision.
  • Store object-storage references rather than file bodies in the relational database.
  • Include a concurrency version on mutable aggregates.

15 Maintainability and testing

The project already separates domain helpers and several feature pages, but the main application file still owns too many responsibilities. The largest application files are approximately 773 lines for src/app/App.tsx and 4,420 lines for the main CSS file. Template contracts are also duplicated in React files.

Recommended frontend decomposition

  • Move permit list, create, edit, detail, workflow, activity, and audit screens into separate feature modules.
  • Define template and directory contracts once in the domain or API contract layer.
  • Route persistence through API clients rather than direct localStorage calls.
  • Split the largest CSS file by stable feature ownership or adopt an approved scoped approach.
  • Add ESLint, a formatter, an application error boundary, and production telemetry.

Test strategy for continuation

  • Keep existing domain tests as behaviour references while server rules are implemented.
  • Add API integration tests against a real test database.
  • Add authorization tests for every role, site, company, assignment, and object scope.
  • Add concurrency tests for duplicate approvals, edits, activation, closure, and numbering.
  • Add file-upload security and object-storage integration tests.
  • Add end-to-end tests for requestor, reviewer, MT Group, PM, assessor, and administrator journeys.
  • Require build, unit, integration, security, and end-to-end checks in CI.

16 Business decisions required

  1. Must every selected child permit be approved before the parent can be approved or activated?
  2. Do parent and child permits have independent approval chains?
  3. What happens to children when a parent is suspended, cancelled, closed, expired, or revised?
  4. Is PM approval performed by the contractor PM, the host, or another configured approver?
  5. Can a Micron administrator override normal approvals, and how must the override be audited?
  6. Which roles can create permits and add daily activity logs?
  7. Which MT Group can close a permit when several groups are assigned?
  8. Should expiry be calculated on access or committed by a scheduled server process?
  9. Can an expired permit be revised, reactivated, or only closed?
  10. Which revision fields become immutable after submission?
  11. What is the required permit-number format, sequence scope, and reset period?
  12. What upload types, limits, retention periods, and malware-scanning rules apply?
  13. What are the audit, privacy, and legal retention requirements?
  14. Which analytics and reports are operational requirements rather than mockups?
  15. Which corporate systems own users, companies, sites, training records, disciplines, and groups?
  16. Does contractor self-registration require sponsor or administrator approval?

Final handoff position

The prototype provides a substantial starting point for frontend behaviour and workflow discussion. The receiving team should preserve confirmed user journeys and visual intent, but it should not reproduce browser persistence or client-side authorization as production architecture. The next release should make the server authoritative for identity, access, workflow transitions, concurrency, files, notifications, and audit history.
